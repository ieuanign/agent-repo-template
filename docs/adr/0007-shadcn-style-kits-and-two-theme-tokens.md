# shadcn-style kits on web and mobile, with one two-theme token file

web uses [shadcn/ui](https://ui.shadcn.com) on Radix, and mobile uses [react-native-reusables](https://reactnativereusables.com) on [Uniwind](https://docs.uniwind.dev). Both read [`packages/design-tokens/theme.css`](../../packages/design-tokens/README.md), whose colours take the kits' own names (`background`/`foreground`, `primary`/`primary-foreground`, `muted`, `destructive`, `border`, `ring` and the rest) and hold a light and a dark value each. Tailwind only styles; a kit supplies the behaviour that is expensive to build twice: focus trapping, keyboard and screen-reader support, portals and popover placement. Both kits copy Tailwind-styled source into the app rather than shipping a styled package, so their classes read our tokens directly, and the two apps share one set of component, variant and colour names. react-native-reusables' primitives follow Radix's API (`asChild`), so Radix on web keeps the two kits alike. Uniwind is stable, compiles `theme.css` unchanged, and is the Tailwind v4 engine react-native-reusables supports.

## Considered Options

- **Hand-built components with the app's own colour names**: rejected. Buttons and inputs are cheap; an accessible select, dropdown menu or dialog is days of work, once per platform.
- **NativeWind v5**: rejected for now. It is still a release candidate, needs a repository-wide `lightningcss` override that also moves web's Tailwind, replaces Inter with the system font on native, and react-native-reusables does not support it. Uniwind's one gap is that editing `theme.css` needs a Metro restart.
- **Base UI**, shadcn's default since July 2026: rejected. Its components take a `render` prop where react-native-reusables takes `asChild`.
- **gluestack-ui v5 and HeroUI Native**: rejected. gluestack stores colours as RGB channels rather than hex, and HeroUI Native brings its own theme and names inside a package.

## Consequences

- **Copied kit files are ours.** Each is edited when it arrives so that every colour and radius class names a token, and renamed to PascalCase under `src/components/` by its atomic tier; oxlint's `unicorn/filename-case` enforces the names. web keeps its reset of Tailwind's own colours, radii and fonts, so a class naming anything else produces no CSS.
- **`theme.css` has two blocks.** `@theme` registers every colour as `unset` alongside the font, radius and spacing tokens, and `@layer theme { :root { @variant light { … } @variant dark { … } } }` holds the values. Uniwind reads this shape natively; web compiles it once its `globals.css` declares `light` and `dark` custom variants. A colour missing from `@theme` would still work on mobile but produce no class on web, so a test in the package checks the registrations and that both themes hold the same keys.
- **Themes follow the device.** With no class on `<html>`, web's variants follow `prefers-color-scheme` on first paint with no script; mobile uses Uniwind's adaptive themes with `userInterfaceStyle: "automatic"`. A user setting, when one exists, sets a `light` or `dark` class on web and calls `Uniwind.setTheme` on mobile. shadcn's own `@custom-variant dark (&:is(.dark *))` is not used: it never matches `<html class="dark">`.
- **Icons come through one `Icon` atom, and the template names no icon library.** In each app `src/components/Icon` is the one place icons are imported: it re-exports the library the project chooses and holds the project's own icons. A copied kit file's icon imports are rewritten to go through it, so the kit's default library is never imported directly.
